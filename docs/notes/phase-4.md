# Phase 4: MAVLink parser, link statistics, link_monitor

## What was built
- `src/link/crc.cpp`: CRC-16/MCRF4XX (X.25), the MAVLink checksum, plus `crc_extra` per message.
- `src/link/mavlink_parser.cpp`: streaming MAVLink v2 parser. Bytes arrive in arbitrary chunks;
  it hunts for the 0xFD magic, waits for a full frame (+13 bytes if signed), checks the CRC
  (including crc_extra), and on any failure skips ONE byte and resumes the hunt.
- `src/link/link_stats.cpp`: per-source (sysid, compid) sequence-gap loss, 8-bit wrap, duplicates,
  and (added this phase) reorder tolerance.
- `src/link/monitor_main.cpp` → `link_monitor`: UDP listener on our own parser (no MAVLink library,
  no MAVSDK). 1 Hz CSV `link_stats.csv`, heartbeat watchdog (> 3 s), clean SIGINT.
- `scripts/netem_loss_test.sh`: PX4 SITL + link_monitor; 20 s baseline, 60 s `tc netem loss`,
  20 s recovery. The loss rule is always removed by a trap.
- Tests: 42 spec tests + `test_parser_robustness.cpp` (6) + `test_link_reorder.cpp` (4).
  Total ctest: **71/71 pass**, 0 warnings, ASan/UBSan clean.

## Measured results
| test | result | evidence |
|---|---|---|
| Live baseline (PX4 → UDP 14550) | 375.5 frames/s mean over 35 s, **0 lost of 14,996**, 0 CRC errors | `runs/link-baseline/link_stats.csv` |

| netem 5 %, fixed estimator | baseline 0.00 %, **netem 4.88 %** (940 lost / 18,313 received), recovery 0.00 %, 0 CRC errors | `runs/link-netem-5pct-20261031-142544` |

Receive rate under netem fell 376 → 310 frames/s, more than 5 %. netem on `lo` also drops PX4 ↔ Gazebo
traffic, which slows the lockstep simulation, so PX4 sends fewer messages. That is not link loss,
and the sequence-gap method correctly does not count it.

## The bug found by measurement
`missing = (seq − last − 1) mod 256` is correct for loss but not for **reordering**. If 12 arrives
before 11, frame 11 gives (11 − 12 − 1) mod 256 = 254 phantom losses. A qdisc on `lo` can deliver
datagrams out of order (they get dequeued on different CPUs). The fix is the RTP / RFC 3550
half-window rule: if (seq − last) mod 256 ≥ 128 the frame is late. Count it in `reordered()`, take
back the one loss charged when it was skipped, and do not move `last_seq` backwards.
- **Rejected:** a 256-bit "seen" bitmap per source. Exact, but more state and more code to explain
  for the same practical result.
- **Not yet measured:** the `reordered` count under netem (the column was added after run 142544).
  `[TBD: measure]` in the next netem run.

## Decisions
- **Own parser instead of the MAVLink C library**: shows understanding of framing/CRC; the test
  vectors (generated by pymavlink) prove byte-for-byte correctness.
- **Append buffer + read index, erase once per push**: O(n) per push, not O(n²) from erasing per byte.
- **Resync = skip one byte after the magic**, not the whole claimed frame: a corrupted length byte
  must not swallow the following good frames (test: one corrupt frame loses only that frame).
- **SO_RCVTIMEO 200 ms + sigaction without SA_RESTART**: the loop wakes up for the 1 Hz report and
  watchdog even with no traffic, and Ctrl-C interrupts `recvfrom` at once.
- **Flush the CSV every second**: the file stays usable if the process is killed.

## Edge cases handled
Garbage between frames (counted exactly in bytes_skipped), frames split across any chunk boundary,
signed frames (+13 bytes), unknown msgid (skipped, counted), bad incompat flags, max payload 255,
seq wrap 255 → 0, duplicates, multiple sources, reordered frames, no heartbeat yet (−1 in CSV).
**Limitation:** ≥ 128 consecutive lost frames look like reordering; the heartbeat watchdog covers outages.

## Interview Q&A
1. **Why is crc_extra needed?** It is a per-message seed derived from the message definition. If
   sender and receiver disagree on a message's fields, the CRC fails instead of silently
   misinterpreting bytes.
2. **How do you resync after corruption?** Drop one byte after the bad magic and search for the next
   0xFD. Never trust the length field of a frame whose CRC failed.
3. **How is loss measured without the sender's cooperation?** From the 8-bit per-source sequence
   number: the gap mod 256. Each (sysid, compid) is tracked separately, duplicates add no loss, and
   late frames are detected with the half-window rule.
4. **What went wrong in the first netem test, and how did you find it?** Measured loss was 70 % for
   5 % injected while the frame rate dropped only 16 %. That mismatch meant phantom losses; the cause
   was reordering producing 254-frame "gaps". Fixed with the RFC 3550 rule plus 4 new tests;
   re-measured 4.88 %.
5. **Why does the receive rate fall more than the injected loss?** netem on loopback also hits the
   PX4 ↔ Gazebo traffic, slowing the lockstep sim. Fewer messages are sent, but none of them are lost.
   The sequence-gap estimator measures the link, not the rate.
